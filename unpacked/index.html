How a subagent runs

AgentTool.execute in tools/agent/agent.ts loads a config via SubagentManager, instantiates an AgentHeadless (one-shot) or AgentInteractive (long-lived), and runs AgentCore.runReasoningLoop in agents/runtime/agent-core.ts. The subagent gets a fresh GeminiChat with its own system prompt — the parent's transcript is not shared. Only the final text returns to the parent. Recursion is blocked by EXCLUDED_TOOLS_FOR_SUBAGENTS.

Qwen Code vs Claude Code

Both are open-source-ish terminal agents. They make different bets on tool surface, context sharing, and where the trust boundary lives.

Where Claude Code is ahead

The matrix above maps both surfaces side by side. This section names the concrete gaps Qwen Code would need to close to match Claude Code as a harness, ordered roughly by impact.

Gap 1 · Tool surface, with no lazy loading

Claude Code ships ~54 built-in tools and partitions them. A small eager hot-path set (Read / Edit / Write / Bash / Agent / Skill / ScheduleWakeup / ToolSearch) lives in the system prompt every turn. The remaining ~25 — notebook, web, plan-mode, task-tracker, cron, MCP-resource, team, push-notification, worktree — are deferred. The model has to call ToolSearch with "select:Read,Edit" or a keyword query like "notebook jupyter"; the matching tool's full JSON schema returns inline and the tool is callable for the rest of the session. Calling a deferred tool without fetching it first throws InputValidationError.

Qwen Code has ~20 built-in tools (core/src/tools/tool-names.ts) and loads every schema upfront via ToolRegistry.warmAll(). There is no ToolSearch equivalent and no deferred concept — discovered MCP tools and project tools join the same eager set. That keeps the harness simple and execution behaviour predictable, but every cold turn pays the full schema cost. Without a lazy-loading mechanism, the surface can't realistically grow past ~30–40 tools before context budgets get squeezed.

Gap 2 · No fork-style subagents

Claude Code's Agent tool has two distinct modes. Pass a subagent_type (Plan / Explore / general-purpose / ...) and you get a fresh window: the subagent starts with zero context and only sees the prompt the parent put in the call — the standard delegation pattern. Omit subagent_type and you get a fork: the subagent inherits the parent's full transcript, shares the prompt cache, runs in the background by design, and is explicitly told to write its tool noise to an output_file the parent is forbidden to read mid-flight. Forks are how a Claude Code session offloads side-quests without dropping the thread.

Qwen Code's AgentTool only implements the fresh-window mode. Every spawn loads a SubagentConfig via SubagentManager and builds a brand-new GeminiChat with the subagent's own system prompt; the parent transcript is never shared. You can pass extra context manually via systemContext / extraHistory, but there is no built-in "continue this thread, just in a sub-process" primitive and no shared prompt cache. The closest equivalent — run_in_background:true — still spins up a fresh window.

Gap 3 · Thinner permission and safety stack

Claude Code carries seven ApprovalMode values (plan, default, acceptEdits, auto, dontAsk, bypassPermissions, bubble — the last being a dedicated escalation channel for subagents asking the parent for permission), an LLM-based yoloClassifier that races a fast-filter and a chain-of-thought against a timeout to decide whether a given command is safe to auto-approve, and a seven-layer safety stack with the sandbox as one layer among many. Anthropic's own design notes target the 93% rate of "pure friction" prompt approvals as the thing this stack is designed to bring down.

Qwen Code has four ApprovalMode values (plan / default / auto-edit / yolo, config.ts:144-148) and a single rule engine (deny > ask > allow > default). There is no LLM classifier, no bubble-style escalation between subagent and parent, and no equivalent to acceptEdits as a separate axis. The rule format is expressive — Bash(ls -l), Edit(/path/*.ts), mcp/resource_read(github.com/*) — but it leans on the user to write good rules ahead of time rather than reasoning about the actual command at the moment of the call.

Gap 4 · Fewer skills, no plugin distribution

Claude Code surfaces 10+ user-invocable bundled skills covering code review (review, security-review, simplify), workflow (loop, schedule), API help (claude-api), and a harness-meta tier (init, update-config, keybindings-help, fewer-permission-prompts — which sweeps your transcripts for prompts you keep approving and proposes an allowlist). It also has plugin namespacing — skills like claude-api and superpowers:code-reviewer ship from separate plugin packages distributed through a marketplace.

Qwen Code ships four bundled skills under core/src/skills/bundled/: batch, loop, qc-helper, review. They are unusually deep per skill — batch is a full parallel-orchestration recipe, review hard-codes the GitHub Create Review API with a "silence is better than noise" guard, qc-helper ships an indexed docs/ tree — but there is no harness-meta tier (no equivalent of update-config, keybindings-help, or fewer-permission-prompts), no security-review counterpart, and no plugin namespacing. User skills land at ~/.qwen/skills/<name>/SKILL.md as a flat list inside a level. The SKILL.md primitive itself is already there; what's missing is the catalog and the distribution channel.

Gap 5 · Smaller hook surface

Claude Code's hook system fires on 27 events with four execution types — shell scripts, LLM calls, webhooks, and subagent verifiers — letting users insert custom checks at nearly every lifecycle point: pre/post tool, pre/post compact, on stop, on user-prompt-submit, on subagent completion, etc. Verifiers in particular let a hook re-prompt the agent if a check fails.

Qwen Code's CoreToolScheduler fires three: preToolUse, postToolUse, postToolUseFailure. That covers the 80% case (block dangerous calls, lint after writes, log everything) but it's not enough for verifiers that need to run after a subagent completes, for hooks that should steer compaction, or for reacting at the user-prompt-submit boundary. Closing this gap is mostly mechanical — the dispatcher exists, the events don't.

Future directions

Where Qwen Code could go next — informed by the gaps above, but pitched as forward-looking work, not catch-up.

infra
Sandbox-first execution

The pieces are already in place — sandboxConfig.command in core/src/config/config.ts already accepts 'docker' | 'podman' | 'sandbox-exec', and the qwen-code-sandbox image ships with the project. What's missing is making sandbox the default and reframing the permission engine around boundary crossings instead of per-tool prompts. Inside a hermetic container the agent can run shells, edits, and network calls with near-YOLO freedom; only egress to the host filesystem, the host network, or the user's git remote should hit an approval. Done well, this is where auto-edit mode finally becomes safe to keep on by default.

runtime
Lazy-loading tool registry

ToolRegistry.warmAll() works fine at 20 tools but won't scale past 30–40 without context bloat on every cold turn. Adding a deferred set behind a Qwen-equivalent of ToolSearch — name-based select: queries plus keyword fuzzy match, returning full JSONSchema inline — would let the catalog grow without paying for it on warm-up. The natural deferred candidates are already obvious: cron tools, MCP-resource tools, future notebook / web-browser / push-notification tools.

runtime
Fork-style subagents

Add a second mode to AgentTool that inherits the parent's transcript and prompt cache instead of starting fresh. This is the missing primitive for "go investigate this side-quest while I keep the main thread" without paying re-priming costs. The hard parts — preventing the parent from tailing the fork's output, surfacing completion as a notification, isolating tool noise — already have a precedent in BackgroundTaskRegistry.

safety
Command classifier on the fast model

Use the lightweightModel Qwen Code already configures for memory tasks to gate borderline tool calls in real time. The classifier reads the proposed command (Bash, Edit, network fetch) plus session context and decides allow / ask / deny — eliminating most pure-friction approval prompts without lowering the floor on actually risky calls. Anthropic's number is that 93% of permission prompts are approved; that's the budget.

ecosystem
Skill marketplace and plugin namespacing

The SKILL.md primitive is solid. What's missing is a distribution channel — a registry, semantic versioning, plugin namespacing (so two skills called review from different sources can coexist as vendorA:review / vendorB:review), and a qwen install <skill> command. The four bundled skills today are deep enough to be a quality bar; the question is whether the community wants to ship the next four hundred.

extensibility
Hook surface expansion + verifiers

Add events for preCompact, userPromptSubmit, subagentStop, and a verifier execution type that can re-prompt the agent if a check fails. The preToolUse / postToolUse / postToolUseFailure trio is the floor — verifiers and compaction-time hooks are the ceiling that turns hooks from "intercept dangerous calls" into "shape the agent's behavior end-to-end."

multi-agent
Coordinator / parallel worktrees

Arena already runs two agents on the same task for comparison; the natural next step is a coordinator that breaks a task into pieces, dispatches workers in isolated git worktrees, and merges results. The Channels package and SendMessage tool give the IPC primitives; what's missing is the orchestration layer and a clean answer to "how do conflicting edits get reconciled?".

memory
Cross-session memory consolidation

Dream mode already runs a lightweight pass between sessions. The forward direction is making this consolidation persistent and queryable — durable memory entries indexed by topic, with the ability for any future session to pull the relevant slice into its system prompt. The memory/extract.ts and memory/governance.ts modules sketch the shape; the missing piece is a retrieval-time query layer.
