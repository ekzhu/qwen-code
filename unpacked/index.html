How a subagent runs

AgentTool.execute in tools/agent/agent.ts loads a config via SubagentManager, instantiates an AgentHeadless (one-shot) or AgentInteractive (long-lived), and runs AgentCore.runReasoningLoop in agents/runtime/agent-core.ts. The subagent gets a fresh GeminiChat with its own system prompt — the parent's transcript is not shared. Only the final text returns to the parent. Recursion is blocked by EXCLUDED_TOOLS_FOR_SUBAGENTS.

Qwen Code vs Claude Code

Both are open-source-ish terminal agents. They make different bets on tool surface, context sharing, and where the trust boundary lives.

Where the designs diverge

Tool loading: eager vs deferred

Qwen Code keeps things uniform — every tool's full JSON schema is in the prompt for every turn. That's fine when you have ~20 tools, and it makes execution behaviour predictable. Claude Code ships ~2.5× more tools and partitions them: a small eager set for the hot loop and a larger deferred set hidden behind ToolSearch. The model has to ask for a deferred tool's schema by name or keyword before it can call it.

The deferred mechanism is a string match ("select:Read,Edit" or "notebook jupyter") — not embeddings. The trade is straightforward: more tools at the cost of an extra round-trip whenever the model needs an unfamiliar one. With prompt caching the schemas only get streamed once; without it, the eager-everything path quickly bloats every cold turn.

Subagent context model

Qwen's AgentTool is the simple model: a fresh GeminiChat, a configured system prompt, the user-supplied prompt, and a filtered tool set (EXCLUDED_TOOLS_FOR_SUBAGENTS blocks recursion + cron + task control). The parent gets a single string back.

Claude Code carries the same fresh-context primitive but adds a second one: forks. Omit subagent_type and the agent inherits the parent's full conversation, sharing the prompt cache. Forks run in the background and are designed so the parent never reads their tool noise — completion arrives as a notification with an output_file path the parent is told not to tail. The fresh-subagent vs fork choice is essentially: do I want this work to share my context, or do I want it shielded from it?

Sandbox: container vs OS-level

Both default to an unsandboxed runtime with an explicit opt-in. Qwen Code (via Gemini CLI heritage) supports both Docker/Podman and Seatbelt — sandboxConfig.command in config.ts takes 'docker' | 'podman' | 'sandbox-exec', and ships a qwen-code-sandbox image. Claude Code skips containers entirely and uses Seatbelt on macOS, bwrap on Linux, plus an out-of-sandbox HTTP proxy with a domain allowlist.

Containers buy you reproducibility and a hermetic FS; the OS-level approach buys lower latency and zero cold-start cost. Neither approach gives the agent a permission-free environment by default — both still consult a deny/ask/allow rule engine for boundary crossings.

Skills — depth vs breadth

Both agents support user-defined skills as Markdown files with YAML frontmatter — Qwen at ~/.qwen/skills/<name>/SKILL.md, Claude at ~/.claude/skills/... (plus plugin-namespaced skills like claude-api and superpowers:code-reviewer). Both auto-surface skills relevant to the current turn through a system reminder, and both let the skill declare an allowedTools allowlist so the skill runtime can't accidentally reach for unrelated tools.

Built-in skill count diverges sharply. Qwen ships 4 bundled skills under core/src/skills/bundled/: batch, loop, qc-helper, review. Claude Code's distribution surfaces 10+ user-invocable skills (visible in the runtime skill list): init, review, security-review, simplify, loop, schedule, claude-api, update-config, keybindings-help, fewer-permission-prompts — plus marketplace plugins.

Quality-wise the comparison is more even than the count suggests. Qwen's bundled skills are unusually deep for so few of them: batch is a full parallel-orchestration recipe with chunking + worker dispatch + result aggregation; review hard-codes the GitHub Create Review API with a "silence is better than noise" guard against AI-comment fatigue; qc-helper ships an indexed docs/ tree the skill loads on demand and can edit ~/.qwen/settings.json for the user; loop has carefully written natural-language interval parsing.

Claude's catalog leans on breadth. It covers the same code-review use case with review + security-review as separate skills, adds a meta-tier that Qwen doesn't have (update-config for harness settings, keybindings-help, fewer-permission-prompts which sweeps your transcripts for prompts you keep approving and proposes an allowlist), and has a domain-specific helper (claude-api) for using the Anthropic SDK. The standalone loop and schedule skills correspond closely to Qwen's loop + the cron tools.

Net read: Qwen's skills are higher-value-per-skill, Claude's catalog covers more surfaces. User-creation ergonomics are roughly equivalent — both want a SKILL.md with a description, an argument hint, and an allowedTools list, and both auto-discover them from a known directory. Claude additionally supports plugin distribution and inter-skill namespacing; Qwen treats every skill as a flat name within a level (project / user / extension / bundled).
